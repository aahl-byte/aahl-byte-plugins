dev-kernel + spec-management

Two-plugin architecture: spec-management (standalone) and dev-kernel (depends on spec-management). Restructured from the standalone ai-dev-kernel repo, following patterns from plan-clarity.

Architecture: Two Plugins, One Dependency

dev-kernel --depends-on--> spec-management init.sh checks for spec-management; prints error and exits non-zero if missing
spec-management (standalone)

Any project can use this independently. Owns all spec scaffolding, maintenance, and tooling.

  • /manage-specs skill
  • spec-tree.py viewer
  • Scaffold templates (ARCHITECTURE.md, INTENT.md)
dev-kernel (pipeline)

Full AI dev pipeline. Reads specs/ at runtime but never writes to it. Requires spec-management at install time.

  • /dk router + 5 phase skills
  • 7 sub-agents (plan + batch)
  • Comms, launcher, validator scripts

Key Structural Decisions

1. Specs separated into own plugin architecture

The spec system (manage-specs, spec-tree.py, scaffold templates) has zero dk-specific logic. Any project can use it for living architecture docs without the pipeline. Separation keeps both plugins focused and independently useful.

2. Agents extracted from skill bodies agents

In the original repo, dk-plan and dk-batch inline their sub-agent prompts within the SKILL.md. Following plan-clarity's pattern, these get extracted into standalone agents/*.md files with frontmatter (name, description, model). Skills reference them via ${CLAUDE_PLUGIN_ROOT}/agents/plan-classify.md. Agents directory stays flat — filenames already carry their prefix (plan-*, batch-*).

3. Scripts namespaced by concern scripts

scripts/dk/ for pipeline utilities (launch, validate). scripts/comms/ for notifications and integrations (ntfy.js today, slack/email later). init.sh stays at the scripts root since it bootstraps everything.

4. References namespaced under dk/ references

The original specs/DK_PIPELINE.md and specs/DK_TEMPLATE.md are pipeline documentation that agents need to read at runtime. These become references/dk/ — the same pattern plan-clarity uses for references/review/COMPONENTS.md.

5. Skills use plugin-relative paths skills

All skill SKILL.md files use ${CLAUDE_PLUGIN_ROOT} for referencing agents, scripts, and references. Portable across global and per-project installs.

2 → Router reads tmp/initiatives/ state files

Comparison: plan-clarity vs. dev-kernel

plan-clarity is a single-skill plugin (one orchestrator, multiple facet agents, one output). dev-kernel is a multi-skill pipeline (router + 5 phase skills, with sub-agents in automated phases) that depends on a separate spec-management plugin.

Design Principles

  • Single entry point — /dk routes everything; users don't call sub-skills directly
  • Agents are data — markdown files with frontmatter, not inline prompt strings
  • References are read-only docs — agents read them, never write to them
  • Scripts namespaced by concern — dk/ for pipeline, comms/ for notifications
  • File-based state lives in the target project — tmp/initiatives/, not the plugin
  • Filesystem boundary between plugins — dev-kernel reads specs/, spec-management writes it
  • Plugin is portable — works via ${CLAUDE_PLUGIN_ROOT}, no hardcoded paths
  • Dependency enforced at init — not at runtime; print and exit non-zero
